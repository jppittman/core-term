# CSI handling audit: inventory, gaps, correctness bugs, and three fixes

**Date:** 2026-09-07
**Scope:** `core-term/src/ansi/{parser.rs,commands.rs,mod.rs}`, `core-term/src/term/emulator/ansi_handler.rs`, `core-term/src/term/modes.rs`, `core-term/src/term/screen.rs` + `emulator/screen_ops.rs`, and the test suites in `core-term/src/ansi/{tests.rs,pict_sgr_tests.rs}`, `core-term/src/term/{core_tests.rs,tests.rs}`.
**Trigger:** requested audit, no specific bug report. Recent history on these files is mutation-testing/test-quality work (#996, #997, #982, #1047), not feature work — this pass is the first pure-correctness look in a while.

## Summary

The state machine and command set are a solid, spec-literate subset of ECMA-48/DEC-VT/xterm — cursor movement, erase, insert/delete, scrolling regions, SGR (incl. 256-color and RGB truecolor), DSR/CPR, DA1, DECSCUSR, and the DEC private modes that matter for a modern terminal (alt screen, bracketed paste, focus events, the mouse-tracking protocols and coordinate encodings a real workload uses, synchronized output 2026) are all implemented, and the screen-level primitives (`insert_blank_chars_in_line`, `scroll_up`/`scroll_down`, etc.) already carry thorough boundary-condition tests. The bugs found were concentrated exactly where the task predicted: in how the parser recovers from something it doesn't understand, and in a handful of parameter-to-command translations in `commands.rs` that had never been exercised by an end-to-end test.

Three bugs were fixed in this pass, each cheap and now pinned by a test:

1. **A malformed CSI sequence corrupted the screen with garbage text**, not just a log line — the single biggest finding.
2. **VPA (`CSI d`) silently reset the cursor's column to 1** instead of moving only the row.
3. **DECSTBM (`CSI r`) with an omitted bottom margin silently fell back to full-screen** instead of "top through the last line," discarding a scrolling region a program explicitly asked for.

Left as findings (not fixed — see §5): no colon (`:`) sub-parameter support at all (the most consequential missing feature, since it's what turns bug #1 into something a real program triggers), `DA2`, `CHT`/`CBT`/`REP`, and dead code for DECSTR (`CSI ! p`) whose enum variant and dispatch handler already exist but are unreachable from the parser.

## 1. Inventory: what CSI dispatches to what

All matching happens in `AnsiCommand::from_csi` (`core-term/src/ansi/commands.rs:600-711`), which switches on `(is_private: bool, intermediates: &[u8], final_byte: u8)`. `is_private` is set by the *first* byte in `CsiEntry` when it's one of `? > ! $ '` (`parser.rs`, `CsiEntry` arm) — note this conflates true DEC private markers (`?`, `>`) with ECMA-48 intermediate bytes (`!`, `$`, `'`) that happen to occupy the same "comes right after `[`" position; see §5.4.

| Final byte | Private/intermediate | Command | Parameter handling |
|---|---|---|---|
| `A` | — | CursorUp(n) | `param_or_1`: 0 and omitted both → 1 |
| `B` | — | CursorDown(n) | `param_or_1` |
| `C` | — | CursorForward(n) | `param_or_1` |
| `D` | — | CursorBackward(n) | `param_or_1` |
| `E` | — | CursorNextLine(n) | `param_or_1` |
| `F` | — | CursorPrevLine(n) | `param_or_1` |
| `G` | — | CursorCharacterAbsolute(n) (CHA) | `param_or_1`; dispatch clamps to `width-1`, preserves row |
| `H` / `f` | — | CursorPosition(row, col) (CUP / HVP) | both `param_or_1` |
| `d` | — | LinePositionAbsolute(n) (VPA) | `param_or_1`; **fixed this pass**, see §4.2 |
| `J` | — | EraseInDisplay(mode) | `param_or(0,0)`; mode via `EraseMode::from` |
| `K` | — | EraseInLine(mode) | `param_or(0,0)` |
| `X` | — | EraseCharacter(n) (ECH) | `param_or_1` |
| `@` | — | InsertCharacter(n) (ICH) | `param_or_1` |
| `L` | — | InsertLine(n) (IL) | `param_or_1` |
| `P` | — | DeleteCharacter(n) (DCH) | `param_or_1` |
| `M` | — | DeleteLine(n) (DL) | `param_or_1` |
| `S` | — | ScrollUp(n) (SU) | `param_or_1` |
| `T` | — | ScrollDown(n) (SD) | `param_or_1` |
| `g` | — | ClearTabStops(mode) (TBC) | `param_or(0,0)` |
| `W` | — | Cursor Tabulation Control (CTC): 0→SetTabStop, 2→ClearTabStops(current), 5→ClearTabStops(all) | other values → `Unsupported` → `Error` |
| `m` | — | SetGraphicsRendition(attrs) (SGR) | full parameter list → `parse_sgr`, see below |
| `n` | — | DeviceStatusReport(n) (DSR) | `param_or(0,0)`; 5 and 6 (CPR) handled in `ansi_handler.rs`, others logged+dropped |
| `s` | — | SaveCursor | none |
| `u` | — | RestoreCursor | none |
| `r` | — | SetScrollingRegion{top,bottom} (DECSTBM) | top `param_or(0,1)`, bottom `param_or(1,0)` (0 = sentinel for "last line"); **fixed this pass**, see §4.3 |
| `c` (not private) | — | PrimaryDeviceAttributes (DA1) | none; responds `\x1b[?6c` regardless of parameters |
| `h` (private) | `?` | SetModePrivate(n) (DECSET) | `param_or(0,0)` |
| `h` (not private) | — | SetMode(n) (SM) | `param_or(0,0)` |
| `l` (private) | `?` | ResetModePrivate(n) (DECRST) | `param_or(0,0)` |
| `l` (not private) | — | ResetMode(n) (RM) | `param_or(0,0)` |
| `q` | `' '` (space) | SetCursorStyle{shape} (DECSCUSR) | `param_or(0,1)` |
| `t` | none or `' '` | WindowManipulation{ps1,ps2,ps3} (XTWINOPS) | ps1 required, ps2/ps3 optional |

That's **29** match arms in the source (one, `H`/`f`, covers two grammar combinations), dispatching to 32 distinct `CsiCommand` variants once `W`'s and `h`/`l`'s internal parameter/private-flag fan-out is counted. Everything else — including any final byte with an intermediate byte this table doesn't list — falls through to the catch-all at `commands.rs:699`, which logs a `warn!` and returns `CsiCommand::Unsupported(intermediates, Some(final_byte))`; the parser (`parser.rs`, `dispatch_csi`) remaps that specific variant to `AnsiCommand::Error(final_byte)` before pushing it. **This fallback is explicit and logged, not a silent drop** — it satisfies the "no silent failures" bar for *syntactically well-formed but semantically unrecognized* sequences. §2 and §5 below are about sequences the grammar itself doesn't accept.

**Parameters.** Up to `MAX_PARAMS = 16` `u16` values are collected (`parser.rs:12`); a 17th+ parameter is dropped with a `warn!` (`add_param`, `parser.rs:95-101`) rather than growing unboundedly or corrupting the ones already collected. An empty parameter (`;;`, or a parameter position with no digits) becomes `0` (`finalize_param`), matching ECMA-48's "omitted = default" convention — most commands then apply their own default via `param_or`/`param_or_1`. Digit accumulation is checked (`checked_mul`/`checked_add`) and clamps to `u16::MAX` with a `warn!` on overflow rather than wrapping (`CsiParam`'s digit arm, unchanged by this pass). Up to `MAX_INTERMEDIATES = 2` intermediate/private-marker bytes are collected the same way. **Sub-parameters (`:`) are not modeled at all** — see §5.1, the most important gap found.

## 2. What real programs send that isn't in the table

Ranked by how often core-term's actual workload (tmux, vim/neovim, less, htop, fish/zsh prompts, `ls --color`, and general shell use) would hit it, cross-checked against xterm's `ctlseqs.html`:

| Rank | Sequence | Who sends it | Status |
|---|---|---|---|
| 1 | SGR sub-parameters, `CSI 38:2:…m` / `CSI 4:3m` (ITU T.416 colon form) | neovim (`termguicolors` on some terminfo paths), foot/kitty-aware programs probing colon support, curly-underline styling | **Not modeled** — every colon byte hits the malformed-sequence path (§3.1, fixed this pass so it now degrades safely instead of corrupting output, but the SGR itself is still dropped) |
| 2 | DA2 (Secondary Device Attributes), `CSI > c` | tmux and other multiplexers, sent at startup to fingerprint the terminal | **Missing.** `>` is folded into `is_private`, so `(true, b">", b'c')` has no arm and falls to `Unsupported`/`Error`. A program that blocks briefly on a DA2 reply (most don't — they time out and assume defaults) would just see the timeout path. |
| 3 | DECSTR (Soft Reset), `CSI ! p` | vim/neovim on cleanup, various "reset terminal state" utilities | **Dead code, not missing code** — see §5.3. `CsiCommand::Reset` and its `ansi_handler.rs:296` dispatch (`emulator.reset()`) already exist; nothing in `from_csi` ever constructs the variant. |
| 4 | REP (Repeat preceding character), `CSI b` | any program using it as a compression trick for runs (increasingly common now that xterm/kitty/foot/alacritty all support it) | **Missing** — final byte `b` isn't in the table, falls to `Unsupported`. |
| 5 | CHT / CBT (Cursor Forward/Backward Tabulation), `CSI I` / `CSI Z` | shells and full-screen apps doing tab-stop-relative layout; less common than plain `\t` but real | **Missing** — neither final byte is in the table. |
| 6 | Kitty keyboard protocol, `CSI u` query/response and `CSI > … u` flags | neovim, kitty, and a growing set of TUI toolkits for disambiguating key events | **Missing**, and explicitly out of scope for this pass per the task (large feature, not a bug). `CSI u` also collides syntactically with plain RestoreCursor's `u` final byte — this needs actual design work, not a quick add. |
| 7 | DECSLRM (left/right margins) and rectangular-area ops (`$`-intermediate family: DECFRA, DECCRA, …) | vim/tmux rarely; some full-screen editors with box-drawing | **Missing.** Same `$`/`'` intermediate-byte confusion as DECSTR applies here too. |

Everything else on the task's checklist — CUP/HVP, CUU/CUD/CUF/CUB, CNL/CPL, CHA, ED/EL/ECH, ICH/DCH/IL/DL, SU/SD, DECSTBM, SGR 256-color and truecolor in `;` form, DSR/CPR, DA1, DECSCUSR, CSI t window ops — **is implemented**, matching the inventory in §1. Of the DECSET/DECRST modes listed in the task, 1/6/7/9/12/25/1000/1002/1003/1005/1006/1047/1048/1049/2004/1004/2026 are recognized *and* tracked in `DecPrivateModes`; two mouse protocols the task didn't ask about but that `DecModeConstant` already names, 1015 (urxvt) and 1016 (SGR pixel position), are recognized only to avoid an "unknown mode" warning — `mode_handler.rs`'s arms for both just log "not fully implemented" and touch no state (`modes.rs` has no `mouse_urxvt_mode`/`mouse_pixel_position_mode` fields at all).

## 3. Correctness bugs found and fixed

### 3.1 Malformed CSI printed the rest of the sequence as literal text (fixed)

**File:** `core-term/src/ansi/parser.rs`. **Severity: high** — this is the one that produces visible screen corruption, not just a dropped feature.

Before this pass, `CsiEntry`/`CsiParam`/`CsiIntermediate` handled any byte outside the grammar they expected (digit, `;`, private marker, intermediate, final byte) by logging a `warn!`, pushing `AnsiCommand::Error(byte)`, and then — critically — resetting the parser straight to `Ground`. Everything after the offending byte, up to the next `ESC`, was then read as plain printable characters. Confirmed with the parser as it stood on `main`:

```
input:  \x1B[38:2:255:0:0mXY
output: [Error(58), Print('2'), Print(':'), Print('2'), Print('5'), Print('5'),
         Print(':'), Print('0'), Print(':'), Print('0'), Print('m'),
         Print('X'), Print('Y')]
```

`"2:255:0:0mXY"` would have been written to the screen verbatim. This is exactly the CLAUDE.md "no silent failures" anti-pattern in its more dangerous cousin form: the failure *is* logged, but the recovery still falls through into a wrong state. Any colon-form SGR (§5.1 — plausible from neovim) or any other byte this parser doesn't accept mid-sequence would trigger it.

**Fix:** added a `CsiIgnore` trap state, matching the standard ECMA-48/DEC-VT "CSI ignore" state (the same recovery xterm/VTE use): on an invalid byte, report `Error` as before, then absorb every subsequent parameter/intermediate byte silently until the terminating final byte, which ends the sequence with no command dispatched (the error was already reported) and returns to `Ground`. `ESC` and a stray C0 control still abort out of `CsiIgnore` exactly as they already did for the other CSI sub-states, so recovery composes with the rest of the state machine.

```
input:  \x1B[38:2:255:0:0mXY   (after fix)
output: [Error(58), Print('X'), Print('Y')]
```

Tests added: `it_should_discard_rest_of_malformed_csi_instead_of_printing_it`, `it_should_recover_to_ground_and_parse_the_next_csi_after_a_malformed_one` (a valid CSI right after a malformed one parses normally), `it_should_abort_csi_ignore_on_esc_and_process_subsequent_csi` (`core-term/src/ansi/tests.rs`). The pre-existing `it_should_report_error_for_unexpected_char_in_csi_entry` (which only checks the immediate `Error` and never exercises what comes after) still passes unchanged — this fix only changes what happens to bytes *after* the one it already covered.

### 3.2 VPA (`CSI d`) clobbered the cursor's column (fixed)

**Files:** `core-term/src/ansi/commands.rs`, `core-term/src/term/emulator/ansi_handler.rs`, `core-term/src/term/emulator/cursor_handler.rs`, `core-term/src/term/cursor.rs`. **Severity: medium** — VPA is less common than CUP, but every real terminal (and xterm's ctlseqs) specifies that it moves *only* the row.

`from_csi`'s `b'd'` arm built `CsiCommand::CursorPosition(param_or_1(0), 1)` — reusing the two-axis CUP variant with the column hardcoded to `1`. Every VPA therefore reset the cursor to column 0, discarding wherever it actually was — the opposite of the one-axis behavior CHA (`G`) already gets right (`cursor_to_column` preserves the row). The bug was locked in by an existing test literally named `csi_d_is_vpa_column_always_1` that asserted the wrong output as if it were intentional.

**Fix:** gave VPA its own `CsiCommand::LinePositionAbsolute(u16)` variant, dispatched through a new `cursor_to_row`/`move_to_logical_row` pair that mirrors `cursor_to_column`/`move_to_logical_col` on the other axis (same clamping: bottom of the scrolling region under origin mode, otherwise bottom of the screen; column untouched).

Tests: parser-level `csi_d_is_vpa_row_only_column_untouched` and `csi_d_default_row_is_1` (both fixed from asserting the bug) in `ansi/tests.rs`; end-to-end emulator-level `it_should_move_cursor_to_row_n_on_csi_vpa_preserving_column` and `it_should_clamp_cursor_at_last_row_on_csi_vpa_if_move_is_too_far` in `term/core_tests.rs`, following the existing CHA test pattern so the fix is checked all the way through to rendered cursor position, not just the parsed command.

### 3.3 DECSTBM with an omitted bottom margin silently reset to full screen (fixed)

**File:** `core-term/src/term/screen.rs`, `set_scrolling_region`. **Severity: medium** — a program that sets a scrolling region with `CSI Pt r` (top only, relying on the documented default of "last line" for the bottom) gets the *wrong* region rather than an error.

`from_csi`'s `b'r'` arm already resolves an omitted bottom parameter to `0` with a comment noting "0 (often means last line)" — but `Screen::set_scrolling_region` never resolved that sentinel. It compared `top_1_based - 1 < bottom_1_based - 1` directly, and `0usize.saturating_sub(1) == 0`, so `t < b` was false whenever `b` was 0 regardless of `t`. The region was then silently replaced with the full screen and a `warn!("Invalid scrolling region...")` — misidentifying a valid, common request as invalid.

**Fix:** resolve `bottom_1_based == 0` to `self.height` before the validity check, at the one place that knows the current screen height.

Tests: `set_scrolling_region_with_bottom_0_means_last_line_of_screen` (`term/screen.rs`, unit-level) and `it_should_scroll_up_within_scrolling_region_with_omitted_bottom_defaulting_to_last_line` (`term/core_tests.rs`, end-to-end: sets `CSI 2r` on a 4-row screen, scrolls, and confirms row 0 — outside the requested region — stays untouched, which the pre-fix fallback-to-full-screen would have scrolled too).

## 4. Existing test-suite quality

The suite (604 tests across the crate; 194 in `ansi::tests` alone) is in good shape overall, consistent with the recent mutation-testing passes — most CSI arms have a dedicated test, and `pict_sgr_tests.rs` runs a pairwise-covering-array check of SGR parameter combinations against a hand-written oracle, which is a genuinely strong piece of infrastructure (not just spot checks). The screen-level primitives (`insert_blank_chars_in_line`, `delete_chars_in_line`, `scroll_up`/`scroll_down`) already have thorough boundary tests: no-op on out-of-bounds rows, capped counts at line/region edges, invalid-region no-ops, off-by-one region-height checks. That test density is almost certainly why this audit's bugs were concentrated in `commands.rs`'s parameter-to-command translation and the parser's recovery path rather than in `screen.rs` itself.

The two weak spots found were both in `ansi/tests.rs`, and both were the two VPA tests fixed in §3.2 (`csi_d_is_vpa_column_always_1`, `csi_d_default_row_is_1`): they asserted the *bug's* output as the expected output, with a comment ("Column is hardcoded to 1") that documented the wrong behavior as if it were a deliberate spec choice rather than flagging it. This is a case worth naming for the mutation-testing effort generally: a mutation test can only catch a regression *from whatever the test currently asserts* — it cannot tell you the assertion itself encodes a bug. Both are now corrected to assert the right behavior instead of pinning the wrong one.

## 5. Findings not fixed in this pass

### 5.1 No colon (`:`) sub-parameter support (highest priority follow-up)

This is the actual feature gap behind bug §3.1. `:` is an ECMA-48 parameter byte (0x3A, same class as `;` and the DEC private markers), used for SGR sub-parameters — most commonly the ITU T.416 truecolor/256-color forms (`CSI 38:2:…m`, `CSI 38:5:…m`) and newer per-style extensions like curly underline (`CSI 4:3m`). This parser has no representation for "these parameters belong to one attribute" — `params` is a flat `Vec<u16>`.

**Do not fix this by treating `:` the same as `;`** (i.e., just adding it as another parameter separator) — that's the tempting cheap fix and it is wrong, not just incomplete. Real emitters of the T.416 form (neovim among them) include the color-space sub-parameter as an *empty* field: `CSI 38:2::255:0:0m` (empty `Pi` between "2" and the RGB triple). Flattening `:` into the same parameter stream as `;` would parse that empty field as a literal `0` and shift every subsequent value by one position, silently producing a *wrong but plausible-looking* color (e.g. reading R from what was actually the empty colorspace slot) rather than failing loudly. That is a strictly worse outcome than today's "drop it, log it" behavior, and it's the kind of bug this codebase's own philosophy calls out specifically (a wrong value that's silently representable is worse than one that panics).

The correct fix restructures parameter collection to preserve grouping (e.g. `Vec<Vec<u16>>`, one inner vec per `;`-separated top-level parameter, split further by `:`) so `parse_extended_color` can tell "3 sub-params" from "4 with an empty leading one" apart. That's real, scoped work — not a one-line change — which is why it's a finding rather than a fix in this pass.

### 5.2 DA2 (`CSI > c`) unimplemented

tmux and other multiplexers query this at startup. Low risk (callers generally time out and assume defaults rather than blocking), but cheap to add once the `is_private`/intermediate representation is untangled (§5.4) enough to give `>` its own case distinct from `?`.

### 5.3 DECSTR (`CSI ! p`) has a dispatch handler but is unreachable

`CsiCommand::Reset` and `ansi_handler.rs:296`'s `CsiCommand::Reset => emulator.reset()` already exist, but nothing in `from_csi` ever constructs `CsiCommand::Reset` — there's no match arm for `!`+`p`. This was tempting to wire up as a one-line fix (the parsing side is trivial given the existing dead code), but doing so without more thought would be a semantics decision disguised as a bug fix: the existing `TerminalEmulator::reset()` (`term/emulator/methods.rs:28`) is written for RIS (`ESC c`, a *hard* reset) and calls `erase_in_display(EraseMode::All)`, clearing the screen. DECSTR is specified as a *soft* reset — attributes, modes, scrolling region, cursor — and should not touch screen content. Wiring DECSTR straight to the existing `reset()` would trade "silently does nothing" for "silently wipes the screen," which is arguably a worse surprise for whatever program sent it expecting soft-reset semantics. Recommend implementing a real soft-reset path (or confirming intentionally that this codebase doesn't distinguish the two) before connecting the parser side.

### 5.4 `is_private_csi` conflates DEC private markers with ECMA-48 intermediates

`parser.rs`'s `CsiEntry` state sets `is_private_csi = true` for any of `? > ! $ '`. Only `?` and `>` (0x3C-0x3F range) are true "private marker" bytes in the DEC/ECMA-48 sense; `!`, `$`, and `'` (0x21, 0x24, 0x27) are ordinary intermediate bytes that happen to introduce a family of sequences (DECSTR, DECRQM, rectangular-area ops, DECIC/DECDC) that this parser doesn't otherwise implement. Today this is harmless — none of those combinations have a match arm regardless of the `is_private` value, so they land in the same `Unsupported`/`Error` catch-all either way — but it's the reason §5.2's DA2 and §5.3's DECSTR both need to reckon with a boolean that's already overloaded. Restructuring this (e.g., storing the actual marker byte rather than a bool, as the file's own "denote before you build" convention would suggest) is a prerequisite for implementing any of §5.1-5.3 cleanly, not an issue in isolation.

### 5.5 CHT/CBT/REP unimplemented

`CSI I` (CHT), `CSI Z` (CBT), `CSI b` (REP) have no match arms at all — straightforward additions once wanted, no architectural blocker, just not exercised yet.

### 5.6 Kitty keyboard protocol / `CSI > u` flags — confirmed out of scope

Per the task, not attempted here. Noted only because `CSI u` (the kitty query/push form) and the already-implemented `RestoreCursor` (also final byte `u`, no intermediate) will need to be disambiguated by parameter shape or a flag-state the terminal tracks, which is real design work.

### 5.7 `screen.rs` at 2434 lines

Outside this audit's direct scope, but worth flagging per prior guidance on file size: `term/screen.rs` mixes grid storage, scrollback, selection, tab stops, and alt-screen management in one file. Not touched in this pass since none of the bugs found were structural.

## 6. What was NOT changed

- Full colon sub-parameter support (§5.1) — real feature work, correctly scoped out.
- DA2, DECSTR wiring, CHT/CBT/REP, kitty protocol (§5.2, 5.3, 5.5, 5.6) — missing features, not bugs; left as findings per the task's instruction not to implement large features in this pass.
- The `is_private_csi` boolean's conflation of private markers and intermediates (§5.4) — a real design smell, but nothing currently depends on distinguishing them, so there is no observable bug to point a test at yet.
